# Nasazení JustKvízu z main

1. Vyžádej si v aktuální konverzaci výslovné schválení konkrétního rozsahu. **PRODUKCE** je https://justkviz.cz, Hosting site `justkviz-v2` a Firebase projekt `filmovy-kviz-v2-staging`. Platí [AGENTS.md](../AGENTS.md).
2. Použij čistý checkout větve `main`. Nejprve zkontroluj `git status`, potom stáhni stav pomocí `git fetch origin` a na čistém `main` použij `git merge --ff-only origin/main`. Při neshodě nebo rozpracované práci nejprve vyřeš stav Gitu.
3. Připrav Node.js 22, Git, `tar`, GitHub CLI a pnpm podle `packageManager`. Přihlas se přes `gh auth login`, nainstaluj uzamčené závislosti pomocí `pnpm install --frozen-lockfile` a přihlas se svým oprávněným účtem přes `pnpm exec firebase login`. Skript přes `gh api` ověřuje poslední běh CI z pushe daného commitu na `main` včetně Quality gate.
4. Spusť v terminálu `NASADIT.cmd`. Pokud aktivní release ještě neobsahuje zdrojový commit, příkaz vypíše jeho ID a verzi a zastaví. Ověř dvojici vydání a konkrétního commitu v dosavadních podkladech (například proti tagu `prod-hosting-2026-11-15`) a spusť `NASADIT.cmd --previous ID_RELEASE CELÝ_SHA_COMMITU`.
5. Vyber schválený rozsah. **1** nasadí web s offline režimem. **2** přidá aktualizaci kódu existujících Gen 2 Functions v `europe-west1`. Změny nastavení v kódu (paměť, timeout, `minInstances`) se nepromítnou. Chybějící exporty zobrazí náhled a příslušný plán je vytvoří. Pro první vytvoření resetEventScores platí zvláštní pořadí popsané níže. **3** přidá pravidla Firestore pro `(default)` a pravidla Storage pro `filmovy-kviz-v2-staging.firebasestorage.app`, pokud čtecí kontrola před `ANO` potvrdí existenci bucketu. Když bucket neexistuje, skript to vypíše, vynechá pravidla Storage a ponechá nasazení pravidel Firestore. Změny nastavení Functions nebo indexů vyžadují vlastní schválený postup.
6. Projdi cíle, počet Functions, orientační čas (2–5 minut na dávku po nejvýše pěti Functions, při čekání na Cloud Build i déle) a seznam souborů změněných od commitu aktivního Hostingu. Rozdílný stav backendu po dřívějším nasazení samotného webu se v tomto porovnání neprojeví. Ulož si zobrazené ID, verzi a vypsaný příkaz návratu.
7. Pokračuj až po kontrole a napsání přesného `ANO`. Sestavení používá čistou dočasnou kopii potvrzeného commitu. Před změnami se opět ověří Git, CI a aktivní Hosting. Při širších volbách se nejprve aktualizují Functions, pak případně Rules a nakonec web. Během aktualizace běží část Functions z nové verze a část ze staré. Functions neaktualizuj v den akce. Zvol ideálně dopolední termín mimo provoz.
8. Po úspěchu otevři titulní stránku, detail existující veřejné akce a přihlášení do administrace. Ověř zobrazení a přístup se svým existujícím účtem. Pro funkční testy, seed a testovací data použij lokální emulátory s projektem `demo-*`.
9. Pokud potřebuješ schválený rollback webu, z čistého a zeleného `main` spusť přesně vypsaný příkaz `NASADIT.cmd --rollback ID_RELEASE CELÝ_SHA_COMMITU`, zkontroluj aktuální a cílovou verzi a potvrď `ANO`. Potom zopakuj kontrolu webu. Tento návrat mění pouze Hosting.
10. Pokud některá část vydání selže, ověř, které části se skutečně změnily, a zastav další pokusy do vyjasnění stavu. Návrat Functions nebo Rules vyžaduje zvláštní schválený postup. Výsledek zapiš stručně do popisu PR.


## Vydání N11 před akcí 3. 12. 2026

Cílit na 1. 12., mimo živou akci. David schválí přesný zelený commit po merge na `main`, čtecí náhledy, projekt `filmovy-kviz-v2-staging`, region `europe-west1`, Hosting `justkviz-v2` a níže uvedené rozsahy. Použít samostatný čistý release checkout a ponechat lokální `main` se dvěma SETUP commity na místě. Po celou dobu musí nasazovat jediný operátor. Mezi posledním čtením a GCF PATCH není serverový zámek. Před zahájením uložit identitu/verzi předchozího Hostingu, generace zdrojů a READY revize dotčených Functions. Uložená revize nebo zdroj musejí být dostupné i pro návrat. Při odchylce inventáře nebo rozběhnuté operaci zastavit vydání.

1. **NASADIT → 2) Web + Functions → `ANO`.** Zkontrolovat celý náhled běžných aktualizací. Pro první vydání N11 očekáváme jedinou novou `resetEventScores` a mezi speciálními `lockEventQuiz`. Při vzniku resetu se nejprve dokončí všechny běžné aktualizace včetně zapisovačů bodů a offline synchronizace. Potom skript vytvoří Gen 2 reset se zdrojem téhož SHA, identitou `saveEventScore` a timeoutem 120 s. Použije GCF CREATE bez volání IAM. Nakonec vydá web. Předchozí verze `lockEventQuiz` nadále zvládne první přiřazení kvízu. Po zkoušce umí odmítnout změnu kvůli zapsaným bodům nebo vazbě na session. Dialog odmítnutí zobrazí a sám nespustí reset ani další pokus. Změnu verze po zkoušce a zahození odložit až po kroku 3. Při selhání před Hostingem zůstává předchozí web, některé aktualizace backendu už mohou být účinné. Zjistit stav a opravit dopředně. Je-li výsledek publikace Hostingu nejasný, porovnat aktivní release s uloženou dvojicí ID/SHA, před opakováním provést nový náhled. Příkaz `NASADIT.cmd --rollback ID_RELEASE CELÝ_SHA_COMMITU` použít jen se samostatným souhlasem a kompatibilním cílovým webem.
2. **Samostatný IAM souhlas pro reset.** Po schváleném přečtení metadat potvrdit, že `serviceConfig.service` vytvořené funkce odkazuje v uvedeném projektu a regionu přesně na `reseteventscores`. Ověřit dosavadní policy, případná zděděná oprávnění a zda veřejný invoker již existuje. Pro chybějící binding schválit a použít `gcloud run services add-iam-policy-binding reseteventscores --project=filmovy-kviz-v2-staging --region=europe-west1 --member=allUsers --role=roles/run.invoker --condition=None`. Zpětným přečtením porovnat celou policy. Handler vyžaduje aktivní členství, `event.manage` i `event.score` pro akci a přesné `SMAZAT`. Pokud IAM selže, krok 3 zatím neprovádět. Před opakováním ověřit skutečnou policy. Návrat pouze nově přidaného bindingu vyžaduje samostatný souhlas a příkaz `gcloud run services remove-iam-policy-binding reseteventscores --project=filmovy-kviz-v2-staging --region=europe-west1 --member=allUsers --role=roles/run.invoker --condition=None`. Již dříve existující grant ponechat.
3. **NASADIT → 4) D2 – pouze lockEventQuiz.** Pro přesný push na `main` musí projít Quality gate i job **D2 Linux lockEventQuiz**. Job vytvoří ZIP, rozbalí ho, nainstaluje závislosti z lockfile a spustí `gcp-build`, který načte jediný export a zkontroluje typ callable a region. NASADIT sestaví ZIP ze stejných Git blobů a před uploadem i před PATCH porovná velikost a SHA-256 s důkazem z aktuálního pokusu příslušného běhu CI. Chybějící log nebo odlišný ZIP vydání zastaví. Přečíst náhled přesné funkce, SHA, velikosti a otisku, uložit předchozí revizi a neměnnou generaci zdroje. Potvrdit přesný text `NASADIT lockEventQuiz <prvních 12 znaků SHA>`. Skript omezí změnu na pole `buildConfig.source.storageSource` existující funkce, zachová `GOOGLE_NODE_RUN_SCRIPTS=gcp-build` a ostatní nastavení. Při odmítnutí nebo neshodě před uploadem neproběhne žádný zápis. Pokud selže upload, nedojde k PATCH. Při chybě po odeslání PATCH nebo timeoutu nejprve ověřit stav operace a poslední READY revizi. Příkaz neopakovat naslepo.
4. **Kontrola bez zápisu do produkčních dat.** Po schválení čtení ověřit metadata ACTIVE, očekávanou novou revizi locku, předchozí a novou generaci, region, identitu služby a nezměněný IAM locku. Porovnat Hosting release/SHA a přesný binding resetu. Web ověřit načtením statického HTML a publikovaného JS. Změnu verze, zahazování bodů a staré offline/rozhodčí požadavky zkoušet pouze na demo emulátorech. Pokud některé ověření nevyjde, datum vydání nepovažovat za potvrzené, zjistit rozsah a podle níže uvedeného postupu vrátit jen postiženou část.

**Návrat jediné D2 funkce.** Pro nouzový návrat provozu nejprve potvrdit z `serviceConfig.service` službu `lockeventquiz`, ověřit READY stav přesné předchozí revize uložené v kroku 3 a schválit její jméno. Poté `gcloud run services update-traffic lockeventquiz --project=filmovy-kviz-v2-staging --region=europe-west1 --to-revisions=ULOZENA_PREDCHOZI_REVIZE=100`. Zkontrolovat metadata směrování a provoz. Toto je dočasné přesměrování. Trvalý návrat zdroje vyžaduje samostatně schválený GCF v2 PATCH na `projects/filmovy-kviz-v2-staging/locations/europe-west1/functions/lockEventQuiz` s maskou `buildConfig.source.storageSource` a předchozí ověřenou trojicí bucket, object, generation. Zachovat konfiguraci, obnovit směrování `--to-latest` až po ověření výsledné READY revize. Pokud předchozí generace není dostupná, připravit a znovu ověřit balíček z předchozího zdroje. Historický lock po návratu opět omezuje změny po zkoušce. Po prvním resetu musí zůstat ochrany epochy u všech zapisovačů. Návrat kódu smazané body ani historii neobnovuje.

**Časový odhad.** Krok 1 podle počtu aktualizací počítá 2–5 minut na dávku pěti funkcí (při 95 aktualizacích asi 38–95 minut plus vytvoření a Hosting). Pro D2 rezervovat přibližně 5–15 minut a zvlášť čas na kontrolu a případný návrat. Skutečný čas ovlivní fronta Cloud Build.

Ověřovací rozhraní popisují [GitHub Actions REST API](https://docs.github.com/en/rest/actions/workflow-runs) a [vydání Firebase Hostingu](https://firebase.google.com/docs/reference/hosting/rest/v1beta1/sites.releases/create). Aktualizace kódu Functions používá [Cloud Functions PATCH s maskou polí](https://docs.cloud.google.com/functions/docs/reference/rest/v2/projects.locations.functions/patch).
